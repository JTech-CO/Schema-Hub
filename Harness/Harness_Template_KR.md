## 0. 사용법

### 0.1 세션 루프
1. **시작**: `PROGRESS.md` 읽기 → 현재 phase·다음 할 일·미결 질문 확인 → 본 문서의 해당 phase 절 + 관련 백서 절 확인.
2. **작업**: 한 번에 한 phase. 각 작업 단위마다 그 phase의 **검증 명령**을 돌려 게이트로 확인.
3. **종료**: `PROGRESS.md` 갱신(완료 체크·다음 할 일·새 미결 질문·결정 로그) → 커밋.

### 0.2 phase 완료 판정
- DoD 항목이 **전부** 충족되어야 완료. 하나라도 미달이면 미완료로 두고 다음 phase로 가지 않는다.
- 게이트를 못 넘는데 우회 충동이 들면 → §3 멈춤 규칙.

### 0.3 의존 순서
{{M1 → M2 → … → Mn}}.
병렬 가능한 구간이 있어도 위 순서를 기본으로 한다. 각 phase의 "진입조건"이 선행 게이트를 명시한다.

### 0.4 `PROGRESS.md` 최소 구성 *(가이드: 상태 인계 파일이 없으면 만든다)*
현재 phase / 직전에 끝낸 것 / 다음 할 일 / 미결 질문 / 결정 로그(날짜·결정·이유). 세션이 끊겨도 **이 파일만 읽으면 이어서 작업 가능**해야 한다.

## 1. Phase별 진입조건 · 할 일 · DoD · 검증

### 1.1 Phase 블록 템플릿 *(복사해서 실제 phase마다 채운다)*

```
### M{{n}} — {{phase 이름}} {{★ ← 핵심/위험 phase면 표시}}
- 진입조건: {{선행 게이트·환경 전제. 없으면 "스캐폴딩 완료".}}
- 할 일: {{만들 파일·모듈을 의존 순서로. a.ts → b.ts → … 형태로 짧게.}}
- 참조: {{백서 절 번호 등}}
- DoD:
  1. {{측정 가능한 게이트 — 명령/숫자/이진 판정. "돈다"가 아니라 "동작이 옳다".}}
  2. {{불변식이 있으면 명시: "…인 경우가 절대 없음".}}
  3. {{...}}
- 검증: {{게이트를 확인하는 실제 명령. 예: `pnpm --filter X test`, `curl …`, 곡선/로그 확인.}}
- 주의: {{흔한 오판·정상 상한·우회 금지 지점. 없으면 생략.}}
```

### 1.2 DoD 작성 원칙
- **측정 가능해야 한다.** 사람이 보고 "잘 된 것 같다"가 아니라, 명령 실행 결과·수치·통과/실패 이진값으로 확인된다.
- **"코드가 돈다" ≠ "기능이 동작한다".** 에러 없이 끝나는 것과 의도한 효과가 나는 것은 별개다. 효과를 직접 보는 게이트를 둔다(예: 성공률·정확도·왕복 일치).
- **불변식(invariant)은 분리해서 명시한다.** "절대 일어나면 안 되는 일"(거짓양성 0, 데이터 유실 0, 권한 상승 0 등)은 일반 DoD와 구분해 두고, 1건이라도 위반 시 통과 금지.
- **정합성(parity) 게이트.** 같은 로직을 두 곳에서 구현하면(언어↔언어, 클라↔서버, 모델↔런타임) 동일 입력에 동일 출력임을 수치로 검증한다. 깨지면 뒤 단계가 전부 오염된다.
- **검증은 재현 가능한 명령으로.** 누가 언제 돌려도 같은 판정이 나오게 한다.

### 1.3 Phase 아키타입 메뉴 *(필요한 것만 골라 §1의 실제 phase로 만든다 / 예시 DoD는 참고용)*

프로젝트 종류에 무관하게 자주 쓰이는 phase 유형. 순서는 대체로 아래를 따른다.

1. **기반/스캐폴딩** — 레포 설정, 패키지/워크스페이스, 빌드·린트·타입 설정, 디렉터리 경계 룰.
   - 예시 DoD: 빌드/린트/타입체크 그린, 경계 위반 시 lint 에러로 차단.
2. **핵심 도메인 로직** — 가치의 핵심이 되는 순수 로직(부수효과 없이 테스트 가능하게).
   - 예시 DoD: 단위 테스트 전부 그린, 결정론(동일 입력→동일 출력), 알려진 케이스와 결과 일치.
3. **데이터/영속화** — 스키마, 마이그레이션, 저장소, ORM.
   - 예시 DoD: 마이그레이션 적용 성공, CRUD 왕복, 스키마가 도메인 타입과 모순 없음.
4. **API/서버** — 엔드포인트, 계약(contract), 헬스체크.
   - 예시 DoD: 기동 + 헬스 200, 핵심 엔드포인트 왕복, 요청/응답 스키마 검증 통과.
5. **핵심 기능 실효 검증** ★ — "돌기만" 하는 게 아니라 실제로 의도한 결과를 내는지 보는 게이트.
   - 예시 DoD: 목표 지표(성공률·정확도·지연 등)가 기준선 도달, 비정상(발산/예외) 없음, 산출물 저장·재로드 시 동일 재현.
6. **통합/정합성(parity)** ★ — 두 구현·두 환경이 일치해야 하는 지점.
   - 예시 DoD: 고정 입력 셋에 대해 양측 출력 일치(완전 일치 또는 허용 오차 내).
7. **UI/프론트엔드** — 화면, 상태관리, 실시간 갱신.
   - 예시 DoD: 빌드 그린, 핵심 플로우 수동 시연 통과, 디자인 토큰 준수, 가로 스크롤 없음 + 기본 접근성(키보드·aria·색 외 표식).
8. **외부 연동** — 서드파티 API, 브라우저 확장, OS·하드웨어 연동 등 우리가 통제 못 하는 표면.
   - 예시 DoD: 실제 대상에서 동작 시연, 대상 스키마/DOM 변경 시 **계약 파일 한 곳만** 수정하도록 격리, 가드레일 준수.
9. **벤치마크/배포/CI** — 성능 측정, 파이프라인, 산출물.
   - 예시 DoD: CI 그린(lint/typecheck/test/build), 벤치 리포트 생성, 배포 아티팩트 생성.

> **실제 phase로 만들 때**: 위에서 고른 유형을 §1.1 블록에 채우고, 추상적 "예시 DoD"를 프로젝트의 **구체적 수치·명령**으로 바꾼다. (예: "목표 지표 도달" → "Beginner 승률 0.85 도달".)

## 3. 멈춤 규칙 (STOP)

### 3.1 멈춰야 하는 상황
- 같은 에러/테스트 실패를 **서로 다른 방법으로 3회** 시도해도 미해결.
- DoD 게이트(특히 불변식·핵심 기능 실효·정합성)를 못 넘는데 우회 충동.
- 불변식(루트 `CLAUDE.md`)을 깨야만 통과 가능.
- 큰 아키텍처 변경이 필요해 보임.
- 외부 제약(필요 자원 없음, 대상 접근 불가, 약관·정책 위반 소지).

### 3.2 멈출 때 절차
1. `PROGRESS.md`에 기록: **증상 / 재현 방법 / 시도한 것들 / 가설 / 막힌 지점**.
2. 사용자에게 위 요약을 보고하고, 선택지가 있으면 제시한 뒤 결정을 요청한다.
3. 결정 전까지 **불변식을 깨는 임시 우회를 만들지 않는다.**

### 3.3 절대 금지
- 테스트 삭제·약화 또는 게이트 수치 임의 하향으로 "통과" 위장.
- 정합성·불변식이 깨진 채 다음 phase 진행.
- 아키텍처·패키지 경계 임의 변경(사용자 승인 없이).
- 시크릿(`.env`)·대용량 산출물(가중치·바이너리 등) 커밋.
- 가드레일 약화(정책 위반·과도 요청·과한 권한).

## 4. 검증 우선순위 (한 줄 요약)
불변식/규칙 정확성 > 핵심 기능 실효 > 통합 정합성 > UX/배포.
앞 단계의 게이트가 깨지면 뒤 단계 작업은 의미가 없으므로, 항상 앞에서부터 굳힌다.
