# 왜 하네스(Harness)인가 — 프롬프트나 스킬이 아니라 '구조'를 쓰는 이유

대상: 개발자, 바이브코더, 그리고 Claude Code 같은 코딩 에이전트로 실제 프로젝트를 굴리는 사람.
근거: 이 글의 설명은 모두 Schema-Hub의 하네스 템플릿(단일 파일판 / 다중 파일 Pack판) 구성을 토대로 한다.

---

## 시작점: "돌긴 도는데 기능은 안 됨"

하네스 템플릿의 첫 문장이 핵심을 찌른다. 각 phase의 "완료"는 코드가 도는 것이 아니라 **측정 가능한 게이트(DoD)를 통과하는 것**이다. 복잡한 시스템일수록 "에러 없이 도는데 기능은 사실상 안 됨"이 흔하고, 게이트로 막지 않으면 그 잘못된 완료 판정이 다음 phase로 전파된다.

바이브코딩은 이 문제를 증폭시킨다. 에이전트가 "다 됐습니다"라고 선언하고, 우리는 그 말을 믿고 넘어간다. 검증이 자기보고(self-report)에 의존하는 순간, 틀린 "완료"가 코드베이스에 쌓인다. 하네스는 바로 이 지점을 막기 위한 장치다.

## 하네스란 무엇인가

하네스는 **"무엇을 만드는가"(백서)가 아니라 "어떻게 진행·검증·복구하는가"(운영 규율)** 를 정의한다. 작업의 내용물이 아니라, 작업을 둘러싼 규율의 골격이다.

말 그대로 '하네스(harness)'다. 등반가를 잡아 주는 안전벨트, 혹은 소프트웨어의 테스트 하네스처럼 — 코드 자체가 아니라 코드가 옳게 만들어지도록 잡아 주는 틀이다. 템플릿에서 이 골격은 세션 루프, 완료 판정(DoD), 불변식, 멈춤 규칙(STOP), 검증 우선순위, 런북, 상태 인계라는 역할별 구성요소로 나타난다.

## 진화: 프롬프트 → 컨텍스트 → 하네스 엔지니어링

AI 출범 이후 "모델을 잘 쓰는 법"은 세 단계로 발달해 왔다.

1. 프롬프트 엔지니어링. 단일 명령문을 잘 짜는 기술. 무상태(stateless)·일회성이고, 표현을 다듬어 원하는 출력을 끌어낸다. 짧은 작업엔 충분하지만, 길고 복잡한 다단계 작업에서는 무너진다. 세션이 끊기면 맥락이 사라지고 "완료"를 강제할 방법이 없다.

2. 컨텍스트 엔지니어링. 컨텍스트 창에 들어가는 모든 것 — 시스템 프롬프트, 예시, RAG로 끌어온 문서, 도구 정의, 메모리 — 을 큐레이션하는 기술. 프롬프트보다 강력하지만 여전히 한 시점의 스냅샷이다. 지금 창에 무엇이 있느냐는 다루지만, 에이전트가 여러 세션에 걸쳐 어떻게 진행하고 무엇을 검증하며 무엇을 절대 하지 말아야 하는지는 강제하지 못한다.

3. 하네스 엔지니어링. 에이전트가 그 안에서 돌아가는 운영 루프 전체를 구조화한다. "지금 창에 무엇이 있나"를 넘어, "이 프로젝트가 세션을 넘나들며 어떻게 진행·검증·복구되고, 무엇을 절대 넘지 않는가"라는 지속적 프로세스를 정의한다. 하네스는 상시 존재하는 절차이고, 컨텍스트는 매 세션 그 절차를 통과해 흐르는 것이다.

핵심 전환은 이렇게 요약된다: "모델에게 뭐라고 말할까" → "창에 무엇을 넣을까" → "에이전트가 그 안에서 돌릴 지속적 프로세스는 무엇인가".

## 어떻게 작동하는가 (템플릿 구성으로 보기)

단일 파일 하네스는 다음 메커니즘으로 작동한다.

- 세션 루프(§0): 시작(`PROGRESS.md`를 읽어 현재 phase·다음 할 일·미결 질문 파악) → 작업(한 번에 한 phase, 작업 단위마다 검증 명령 실행) → 종료(`PROGRESS.md` 갱신 후 커밋). 이 루프가 에이전트를 "재개 가능"하게 만든다. 세션이 끊겨도 이 파일만 읽으면 이어서 작업할 수 있어야 한다.
- DoD 게이트(§1): 완료는 측정 가능해야 한다. 사람이 "잘 된 것 같다"가 아니라 명령 실행 결과·수치·통과/실패 이진값으로 확인된다. "코드가 돈다 ≠ 기능이 동작한다"를 전제로, 효과를 직접 보는 게이트(성공률·정확도·왕복 일치)를 둔다.
- 불변식(invariant): "절대 일어나면 안 되는 일"(시크릿 커밋 0, 데이터 유실 0, 권한 상승 0 등). 일반 DoD와 분리해 두고, 1건이라도 위반되면 통과 금지. 다중 파일 Pack에서는 `INVARIANTS.md`에 INV-n으로 등록하고 DoD에서 `(INV-3 준수)`처럼 인용한다.
- 정합성(parity) 게이트: 같은 로직을 두 곳에서 구현하면(언어↔언어, 클라↔서버) 동일 입력에 동일 출력임을 수치로 검증한다. 깨지면 뒤 단계가 전부 오염된다.
- 런북(§2): 증상 → 원인 → 조치 표. 처음 겪은 이슈를 기록하고, 반복되면 행으로 승격한다. 반복되는 고통을 "알려진 처치"로 바꾼다.
- 멈춤 규칙 STOP(§3): 같은 실패를 서로 다른 방법으로 3회 시도해도 미해결이거나, 게이트를 못 넘는데 우회 충동이 들거나, 통과하려면 불변식을 깨야 할 때 멈춘다. 멈출 때는 증상·재현·시도·가설·막힌 지점을 기록하고 사용자에게 보고한다. 그리고 절대 금지: 테스트 삭제·약화나 수치 임의 하향으로 "통과" 위장, 정합성·불변식이 깨진 채 다음 phase 진행, 시크릿 커밋.
- 검증 우선순위(§4): 불변식/규칙 정확성 > 핵심 기능 실효 > 통합 정합성 > UX/배포. 앞 게이트가 깨지면 뒤 작업은 의미가 없으니 항상 앞에서부터 굳힌다.

다중 파일 Pack은 여기에 **관심사 분리**를 더한다. 매 세션 바뀌는 것(`PROGRESS.md`)과 거의 안 바뀌는 것(`HARNESS.md`·`INVARIANTS.md`)을 분리하고, 에이전트를 정확히 한 파일로 보낼 수 있으며("M3 작업 시 `phases/M3.md`만 본다"), 누적되는 런북·결정 기록(ADR)은 별도 파일에 쌓는다. 또한 `CLAUDE.md`가 매 세션 자동 로드되는 최우선 계약 역할을 하고, `GLOSSARY.md`가 용어를 고정한다. 그리고 증거 기반 완료 — 게이트 통과를 주장할 때 명령과 출력을 남긴다. 증거 없는 완료 주장은 미완료로 친다.

## 프롬프트·스킬과 무엇이 다른가

프롬프트는 휘발성이다. 강제력도, 세션 간 상태도, 복구 절차도 없다. 완료는 자기보고에 의존한다. 길고 위험한 프로젝트에는 부족하다.

스킬은 특정 작업 유형을 위한 재사용 가능한 능력/절차다("docx 만드는 법"처럼). 필요할 때 로드되는 "어떻게 이런 일을 하는가"의 묶음으로서 훌륭하다. 하지만 스킬은 능력에 관한 것이지, 장기 다단계 프로젝트의 규율·상태·금지선을 통치하는 것이 아니다. 스킬이 "이런 종류의 작업을 어떻게 수행하나"에 답한다면, 하네스는 "이 프로젝트 전체가 여러 세션에 걸쳐 어떻게 진행·검증·복구되고 안전하게 유지되나"에 답한다. 둘은 경쟁 관계가 아니라 보완 관계다 — 하네스가 규율의 골격을 잡고, 그 안에서 개별 작업은 스킬로 수행할 수 있다.

하네스의 강점을 구체적으로 보면:

- 재개 가능성: 세션이 끊겨도 `PROGRESS.md`만 읽으면 작업을 잇는다.
- 측정 가능한 완료: 게이트가 거짓 "완료"를 막는다.
- 안전·금지선: 불변식 + STOP + 절대 금지 목록이 통과 위장·테스트 약화·시크릿 커밋·경계 파괴를 막는다.
- 복구: 런북이 반복 이슈를 처치로 바꾸고, STOP 절차가 무의미한 헛수고(thrashing)를 끊는다.
- 일관성: 용어집 + 불변식이 세션 간 표류를 막는다.
- 감사 가능성: 증거 기반 완료 + ADR 결정 로그로 "왜 이렇게 했는지"가 남는다.
- 복잡도에 맞는 확장: 작은 프로젝트는 단일 파일, 길고 복잡하면 다중 파일 Pack.

## 무엇을 언제 쓰나

단일 파일 하네스는 작고 짧은 프로젝트용이다. 채울 것만 채우되, 게이트(DoD)·멈춤 규칙·검증 우선순위의 골격은 유지한다 — 이 골격이 하네스의 실제 가치다.

다중 파일 Pack은 복잡하고 장기적인 프로젝트용이다. 관심사 분리, phase별 파일, 누적되는 런북·결정 기록이 세션이 끊겨도 일관성과 검증 규율을 지켜 준다.

## 결론

프롬프트는 모델에게 지금 무엇을 말할지 정한다. 스킬은 어떤 작업을 하는 재사용 가능한 방법을 준다. 하네스는 프로젝트 전체에 지속적인 운영 규율 — 어떻게 진행·검증·복구하고 금지선을 절대 넘지 않을지 — 을 부여한다. 그래서 "완료"가 진짜 완료를 뜻하게 만든다. 시스템이 복잡할수록, 그리고 사람이 손을 덜 댈수록, 이 차이는 결정적이 된다.
